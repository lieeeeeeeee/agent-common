# ADRの作成

後から人間が読み返したときに、何を・なぜ決め、何を決めていないかをそのADRだけで読み取れるADRを作る。プロジェクトにADRの規約・雛形・採番の定めがあれば、本Skillと異なる点はそちらに従う。

## 必ず満たすこと

* 長期間守る意思決定だけを書く。作業の完了で役目を終える情報は書かず、作業中に守る条件は決定として書く。チケット・PR・Issue の番号は書かない。
* Context には、このプロジェクトで実際に起きていて、この決定で解消する問題を書く。仮定の一般論で済ませない。
* 前提にする他のADRの決定は内容を要約して書き、参照先を読まなくても判断を追えるようにする。
* 事実は実コードまたは一次資料と照合し、出典を確認日とともに References 節に載せる。第三者が後から確かめられない事柄を根拠にしない。
* ADR以外への参照は本文に書かず References 節に置く。関連するADRとその関係は関連ADR節にまとめる。
* 参照先は、加筆やファイル移動の後も一意に定まる書き方で指す。物理行番号や章番号だけで指さず、他のADRの決定は「ADR-NNN の Decision 項N（章題）」の形で指す。
* 未確定事項が残る場合は、status を Accepted にせず Proposed にする。

## 原則として満たすこと

満たさない項目があれば、理由をユーザーへの報告に示す。

* 決定は、実現方式を縛らない粒度で書く。採用した実現方式を別の方式に置き換えたときに本文の書き換えが必要になる記述は、ADRに書かない。
* 決定の適用範囲を書く。Decision の末尾に「本ADRで決定しないこと」を置き、各事項を決める実在の文書を名指しする。
* 例外を設ける場合は、その例外が失効する条件を書く。
* 同じ対象はADR内でも既存のADRとの間でも同じ用語で表し、タイトルの付け方を既存のADRと揃える。更新のたびに書き換えが必要になる情報を本文に置かない。

## 雛形と配置

* `docs/adr/NNN-<slug>.md` に置く。NNN は既存の最大番号の次の3桁の連番、slug はタイトルを表す英小文字のケバブケースとする。
* frontmatter に id（NNN）、status（Proposed または Accepted）、date（作成日。YYYY-MM-DD）を置く。
* 見出しは `# ADR-NNN: <タイトル>` とし、本文は日本語で次の節をこの順に置く。
  * Context：解消する問題と、今決める理由
  * Decision：決定と、それを選んだ理由。決定ごとに `### N. <章題>` の見出しを付け、末尾に `### 本ADRで決定しないこと` を置く
  * Consequences：決定を適用した後に生じる良い影響・悪い影響・トレードオフ
  * Alternatives Considered：検討した選択肢と、採用しなかった理由
  * 関連ADR
  * References

作成・変更するのは新しいADRのファイル1つだけとする。作成したADRのパスを示し、ADRに書かなかった実装の詳細があればその移し先（仕様書・PRの説明・コードコメント）を、未確定事項が残っていればその内容を添える。
